## [Unreleased]

## [0.11.0] - 2026-11-22

### Highlights
- A failed deploy says why. The one-line summary names the cause the log holds (the failing test, the TypeScript error, the migration error, the refused rule) instead of the step alone, and the same text reaches the dashboard, the GitHub commit status and the ops endpoint.
- GitHub checks without GitHub Actions: every git deploy posts `powder/deploy` and `powder/test-gate` on the commit, so a commit or pull request shows a check from powder itself. The app's ci tab shows powder's own checks first.
- A failed deploy keeps its commit, its log shows once, lists order by when a deploy was queued and show how long it waited, and a deploy stopped by the watchdog says so.
- The servers list shows every URL of every app, read from the server's real proxy config, including named nginx upstreams and `map $host` routing.
- Cloning an app's repository from the dashboard never moves or removes an existing directory: it clones only into a new `src/`, and a preview's cleanup removes only what powder can prove it created.
- One click copies an error, a log or a command wherever the dashboard shows one.
- The server check follows the server's real setup, and the setup checklist names what is actually missing.

### Fixed
- The container page reads the app's real git checkout: `src/` when it is one, else the app dir when that is the checkout (one rule, `lib/app-checkout.ts`, the same shell line the deploy runs, pinned by a test that runs both on the same directory trees). Before, the page and the repo card tested only `<app dir>/.git`, so an app in the standard `src/` layout showed "not git-tracked" with no branch, commit or "remote has new commits", and an app with an older layout's `.git` left in its app dir showed that stale commit instead of the deployed one. The stale `.git` is now ignored and named on the page.
- The repo card's **clone** action no longer moves the app dir aside. It clones into a new `<app dir>/src` (via a temp dir in the app dir, link-checked, then renamed) and touches nothing else; the route refuses with the reason, before writing anything, when the app has a checkout in `src/` or in the app dir, when `src` exists without being a checkout or is a symlink, or when the layout cannot be read, and the clone script checks the same again on the server. The clone holds the app's deploy lock (waiting at most 20 s, so a running deploy makes it refuse rather than run past the request); its temp clone dir, marked before git runs, is removed when the script exits or is killed, and one a killed run left is removed by the next run (exact name, marker). The clone reads the deploy key from a temp file outside the app dir (removed by the clone script when it exits, and by the route's own cleanup, which also covers a script that refused to start before it could), and `<app dir>/.deploy-key` is re-planted only after the clone is in place, so a refused clone leaves the app dir exactly as it was. When that key cannot be written, the answer says the clone is in place and the card offers to write only the key. Before, an app in the `src/` layout looked untracked, and confirming the action renamed the whole app dir (runtime compose, deploy key, data dirs) to `.before-powder.<time>` and put a fresh clone in its place. The repo card now says in one line where the checkout is, or why there is none.
- A clone made for `/new` or a preview carries a marker (`.git/powder-clone-target`, naming the app or the preview row; a temp clone dir names its owner in `.powder-clone-owner`, written before git runs). Nothing is moved or removed by its name alone: only a directory whose marker names the exact owner, checked right before. Every refusal check runs before the first change, so a refused clone leaves the app directories as they were, and the preview spin fails with the reason; a link-check refusal after the temp clone exists removes only that marked temp clone. Clone scripts report their outcome through the exit code and one status line carrying a random value per call: the value reaches the script on stdin (never its command line), and a script that does not get a valid one within 10 s refuses before doing anything; the script's stdout carries only that line, and git and the link checks run in subshells with that channel closed and their output on stderr, so neither repo content nor a process left running can forge the outcome, and an interrupted run still reports it. An app's clone only ever goes into a path that does not exist; a preview's re-clone moves its own marked directory aside and keeps only the newest such copy. A failed first spin removes only what that spin put in place (nothing when its clone was refused or never ran), and only by the marker; /new removes a clone it placed and then refused, so the name can be retried. Teardown removes a preview's containers, directory and marked copies only by the marker; otherwise the page says it left the directory in place and, when containers of the preview's project are still there, how many (they may still serve the preview's address) and the command to find them; when the removal did not run or did not answer, it says that nothing is known. Clones of one target hold a server-side lock (20 s wait), and a dead temp clone of the same owner (exact name, marker) is removed by the next clone. Clone targets must be one plain directory directly under `/opt/apps`. A preview row set up again (a failed first spin, a missing compose file) re-runs the name checks of a new preview, and the error says what to do by hand. `/new` refuses a name any preview row has, and the adopt flows refuse a container whose compose directory is under `/opt/apps/pv-*`. Before, a preview row left failed under an old-style `<app>-<branch>` name could, on the next push to that branch, rename the directory of an app later created under the same name and clone the preview in its place.
- The container page's git status no longer runs `git fetch` on page load. The remote's tip of the upstream branch comes from `git ls-remote`, which writes nothing to the checkout, and `git status` runs without optional locks, so a page load cannot take the index lock or a ref lock a deploy's sync needs at the same moment. The read uses the deploy key the way the deploy does, with no prompt and a bounded ssh connect. When the remote cannot be checked (ls-remote failed, the branch is not on the remote, no upstream branch), the page says "could not check the remote" with the short reason instead of showing nothing, which read as up to date.
- A failed deploy's one-line summary names the cause the log holds instead of "failed during: <step>" or a wrong guess. One function (`summarizeDeployFailure`, `lib/deploy-failure.ts`) reads it, by the failed step first and then by the evidence in that step's own part of the log: a build failure only from the build (the Dockerfile `RUN` step BuildKit reports as failed and its own lines, read by the same module as the dedicated builder's verdict, `lib/buildkit-log.ts`), a test gate failure only from the tests (the runner's `N failed` line and the first failing file, a located type error, or the gate script's last failure line), a failure after the swap only from the containers. So a build tool's own "worker exited with code 1" no longer reads as a crash-looping container, a test that prints `ECONNREFUSED` on purpose no longer reads as an unreachable database, and colour-coded test output no longer reads as a heap limit (terminal escapes are stripped before any rule runs). When powder itself stopped the step (a `preflight:` line, a guard's refusal, `[build-cache] refusing`, `[migrate] ... cannot ...`, `swap-check: FAILED (...)` with the candidate's own last error line, the `[deadline]` line), the summary is that line. The git-auth preflight's failure is named again (`git auth failed: powder cannot read the git remote ...`): it had stopped matching once the script cut git's output. "failed during: <step>" now repeats the step as the deploy page's banner shows it (`docker compose build (local build)`). The `heap-oom:` and `container-oom:` prefixes are unchanged. The cause comes first (a failed `RUN` step reads `<its failing lines> (the Dockerfile step RUN <command, cut at 40 characters>)`), so it survives the 140-character GitHub commit status. A package manager's own "command failed" trailer never stands for the cause: the line above it does. The test gate's fallback reads only the last lines above the gate's own `FAILED` line (the gate script's labelled failure line or a shell error), never stderr from the middle of a passing run; a bare `Killed` line just above the gate's end (when no test failed) or exit 137 is `container-oom:`, worded with the exit code the gate really had. vitest's unhandled errors name the file they came from, and node:test's `not ok` lines name the first failing test and the count. A `[migrate] ... cannot ...` line leads with the database's own error, and a compose guard refusal with the rule it broke. A build that could not reach its database or a service while it built (a page export) leads with the connection code (`ECONNREFUSED`, `ENOTFOUND`, `ETIMEDOUT`, `EAI_AGAIN`) when it sits within a few lines of the failing lines of the same step. A step name that redaction would change (a trailer forged by build output) is stored, shown and sent as `unknown`. Every fragment the summary quotes from the log is cut from the already-redacted line, so a cut can never keep half a credential (for example a URL's `user:password` without its `@host`), and a connection error never shows a URL's `user:password` as its address. The summary is what the deploy page, the copied error block, the GitHub commit status and the ops endpoint event carry, so all of them change with it; stored summaries of past deploys stay as they are.
- The ops endpoint event of a failed deploy (from the runner, and from the watchdog with step `watchdog` or `queue`) names its step in two ways: `error` reads `failed during: <step> · <summary>` when the step is known (the step written exactly as before, so a receiver that reads it up to the `·` keeps working; a summary that only names the step is sent as `failed during: <step>` alone; any failure with no known step, such as a catch-up deploy given up before it started or an SSH or setup error before the deploy script ran, carries the summary alone), and the new fields `failedStep` and `exitCode` carry the step and its exit code. Only the event changes; the stored summary, the dashboard and the GitHub status keep the summary. `GET /api/internal/deploys` returns the same `failedStep` and `exitCode` next to `errorSummary`, so a receiver that backfills a missed event reads them too. Documented under "Ops endpoint reporting" in `docs/SELF-HOSTING.md`.
- A run's internal marker lines (the synced-commit and built-commit markers, and the dedicated builder's own setup marks) no longer show in the deploy log or the stored error of a failed deploy: one rule (`stripStabilityMarkers` and its live counterpart) drops every marker of the run on both paths.
- A failed deploy no longer goes without a failure event when the database's reply to the failed result was lost: the retry found the row already failed and sent nothing (the watchdog does not reap a failed row). The runner now tells a row holding its own result (the same status and error it sent: the runner sends the event) from a row the watchdog failed (one of the exact notes the reap writes, never a prefix the app's log could print: the reap sent the event), from the row it already reads; a write that gave up leaves the row running for the watchdog, whose reap sends the event. One case still sends none: a failed result that was written while every retry of it, including the late read, failed.
- One duration format (`formatDuration` in `lib/format.ts`) on the deploys list, the deploy page and the ci tab: the deploy page rounded to whole minutes (90 s showed "2m" while the list showed "1m 30s").
- The "deploy previews of other branches" toggle says why previews cannot work when the app's server has no Traefik or no base domain (the reason the webhook gives when it skips a preview, from `GET /api/projects/<id>` as `previewBlockReason`), and cannot be switched on there; previews already on can still be switched off.
- A failed deploy's page no longer offers "roll back to <sha>" when that is the version already running. When the deploy stopped before the swap and no deploy of the app since the last good one succeeded or may have swapped, the page says the running version was not changed instead; `GET /api/deploys/<id>` returns `rollbackUnchanged`. Which steps come at or after the swap is the deploy runner's own list, now in `lib/deploy-swap.ts`; an unknown step, a post-swap check (health check, image readback) or a deploy the watchdog stopped still offers the rollback.
- A deploy the watchdog ends says why and raises a failure event. The row gets a failed step (`watchdog` for a running deploy, `queue` for a queued one no worker claimed) and a one-line summary from the same limits the reap uses (for example "stopped by the watchdog: no heartbeat for 7 minutes" or "never started: queued for 181 minutes and no deploy worker claimed it"), so the deploy page shows its failure banner. The ops endpoint gets the same failure event a normal failure sends, once per reaped deploy: a late failure from an executor that was still alive sends no second one. GitHub gets the row's own summary (a never-claimed deploy no longer reads "stopped reporting"). These writes run after both reaps, so the reaps are still never delayed.
- The author filter on the deploys list matches every deploy of a person. It matched only `webhook:<login>`, so group pushes (`webhook-group:`), catch-ups and manual deploys were hidden, and the dropdown offered commit-author logins that could never match. One parser of `triggered_by` (`parseTrigger` in `lib/deploy-status.ts`) now drives the "triggered by" label, the filter (every push-like prefix for a login; `manual:`, `wizard:` and older bare emails for a user) and the dropdown, which `/api/deploys-list` returns as `authors` (`push:<login>` or `manual:<user>` values; a bare login still means a push).
- Deploy lists show queue time and keep push order. The deploys list, an app's deployments tab and overview, the ci tab's checks and the activity feed order, paginate and date deploys by `queued_at` (when the deploy was asked for) through one rule (`lib/deploy-order.ts`), instead of `started_at`, which the worker resets when it claims a deploy. A deploy that waited two minutes or more shows "waited 12m" on the deploys list, the deploy page and the deployments tab; duration stays build time. A queued deploy's page says "queued for" from the push, a running one "running for" from the claim. The `/api/deploys-list` cursor is now the last row's `queued_at` and id (an ISO timestamp is still accepted).
- A failed deploy's log is shown once. A step failure's `error` held the step's whole log, which `output` holds too, so the deploy page doubled every section, the section count, copy and download. The runner now stores only the end of it in `error` (the last 60 lines, at most 8 KiB) when every line is already in `output`, and keeps any error that says something the output does not; the deploy page shows the error in front of the output only in that case, so older rows render once too. The per-app deployments tab shows the one-line summary, the failed step with its exit code and the end of the log (scrolled to its last line) with a link to the full log, and `GET /api/projects/<id>` sends `errorSummary`, `failedStep`, `exitCode`, `logTail` and `logCut` per deploy instead of the whole `error` (masked on read, read from the last 64 KiB of each column). "copy error" on both pages copies the summary and the last lines of the log instead of megabytes.
- A failed deploy names its commit. The commit the run built is stored in `deploys.built_sha` (migration `0070`, nullable, no default), written on success and on failure; `git_sha` keeps meaning the commit that went live, so rollback targets, the ci tab's deployed commit and the last-good lookups are unchanged. The deploys list, the deploy page, the copied error block, the "debug this deploy" prompt, the activity feed and the ops-hub deploy event name a deploy's commit through one function (`lib/deploy-commit.ts`): the live commit, else the built one, else the commit the push requested, labelled as requested. The deploy event gains `shaSource` (`built` or `requested`).
- The build host cap prune keeps up with a burst of builds. Its 1h gate between prunes and its 1h age floor were fixed numbers, so on a host whose root disk filled faster than they allowed the disk neared full between two prunes. Each prune that holds the build slots now records the root disk it left; with the cache over its cap and the root disk at 75% or more and higher than that prune left it, a run at least 15 minutes later prunes again instead of waiting out the 1h gate (from 85% the gate is skipped, as before). With the root disk at 75% the age steps go on below 1h to 30m and 15m, each only while the disk is still at 75%. Under 75%, on a disk that is not rising, or one filled by something other than the cache, the gate stays 1h, so a quiet host is not pruned after every build.
- The status counters on the apps list no longer leave one counter alone on a second row: the grid follows the number of states, in one row on wide screens and an even grid on narrow ones.
- Copy buttons that failed without saying so (restore commands, DNS record values, the preview TXT challenge and others) now say when the clipboard refused, and select the text so it can be copied by hand.
- The dashboard no longer lets the window scroll into empty space below a long list: the page's scrolling area now contains the visually hidden elements inside it.
- The server check and everything that attaches a container for Traefik follow the server's real Traefik setup. One rule (`lib/traefik-network.ts`) reads the network Traefik routes over from the running `traefik` container: its `--providers.docker.network` flag, else `providers.docker.network` in its mounted `traefik.yml`, `traefik.yaml` or `traefik.toml` (YAML merge keys, TOML literal strings, keys in any case), else `web`. Only those two declarations move powder off `web`: a network Traefik is merely attached to is reported ("set providers.docker.network to let powder route apps over it") and never used, and a network of another compose project than Traefik's own is never even reported, so a Traefik attached by hand to one app's network cannot open that network to every app. On Traefik servers the check requires the network powder routes over and Traefik attached to it; a missing `web` is an info line when Traefik routes over another network, and "fix missing pieces" no longer creates `web` there. New apps (`/new`), previews, URL snapshots and the rollback bridge join that network, and the app template and previews set `traefik.docker.network` when it is not `web`, so an app created on such a server is reachable once a domain is attached. The compose guard accepts the network for that server's apps without `POWDER_SHARED_NETWORKS`. Where Traefik runs on `web`, the rendered compose and the commands are byte-identical to before. The answer is cached per server and stored with its source in `servers.traefik_network` and `servers.traefik_network_source` (migration `0069`, nullable, no default) for the deploy's compose guard, which adds no SSH call.
- The Traefik file provider and the dynamic dir are required only on a Traefik server where a domain redirect is set up (a www mode other than none, or custom redirects), since only redirects use them; elsewhere they are info lines saying redirects are unavailable there until a file provider is configured. `bin/server-bootstrap.sh` takes the same fact as `--redirects yes|no` (default `yes`). A red check result saved under the older rule (`web`, the file provider or the dynamic dir required regardless) shows as "not checked yet" until the next check.
- "Fix missing pieces" no longer adds a second rotation for the Traefik log or a second prune cron: another file in `/etc/logrotate.d` that names `/var/log/traefik`, or a line in `/etc/crontab` or another `/etc/cron.d` file that runs `powder-image-prune`, counts as handled (the check reads the path, not the file name, and each step checks again before writing). Only files the daemon really loads count: in `/etc/cron.d` names of letters, digits, `_` and `-` only (cron's run-parts naming rule, so a `powder-image-prune.bak-x` copy is not a cron file), and in `/etc/logrotate.d` none with one of logrotate's default taboo extensions (`.dpkg-old`, `.rpmsave`, `~` and the rest); a commented-out line never counts. When powder's file and another one both exist, the check warns and names both. An existing Traefik not attached to its network is reported with the `docker network connect` command and never changed.
- The server check no longer fails a server for a docker network nothing on it uses. `/new` now creates `web` (and `internal` when the app opts into the shared internal network) on the server before anything else, with the server bootstrap's own command, and stops with the reason when it cannot. So `web` is required only on Traefik servers, where Traefik and the apps, previews and snapshots it routes sit on it; on `nginx` and `nginx-container` servers a missing `web` is an info line, and a missing `internal` is an info line everywhere (the dashboard and `bin/server-bootstrap.sh` alike). The Traefik dynamic dir stays required on Traefik servers, because domain redirects are written there. Each missing piece now says what needs it.
- The setup checklist names what the server check found missing and where, for example `the Traefik file provider folder missing on srv-1`, then the first piece with its reason, and its action opens that server's check (`/servers/<id>#server-check`). It reads "install Docker and the proxy" only when Docker, the compose plugin or the Traefik container is missing. The check now stores its missing pieces (`servers.check_missing`, migration `0068`, nullable, no default). A red result saved before this release was computed under the stricter rule, so it shows as "not checked yet" with "check now" until the next check (the background re-check runs on the next server sync); a saved green result stays green.
- "get told when a deploy fails" is done when any route really carries failed deploys, and names it: a webhook target for every app, an email target for every app while SMTP is configured, `POWDER_NOTIFY_WEBHOOK_URL`, or ops endpoint reporting (`POWDER_HQ_INGEST_URL` with `POWDER_HQ_INGEST_TOKEN`). Before, an install that sent failures only to its ops endpoint was told to add a target, and an email target without SMTP counted although it sends nothing. One function answers it (`deployFailureRoutes`); only the route names reach the page, never a URL or token.
- A deploy swap can stop the old container without losing requests (`POWDER_DRAIN`, **off by default**: with it unset the deploy script and the Traefik labels are byte-identical to before; `canary` = only the apps named in `POWDER_DRAIN_APPS`, `on` = every bridged app). With it on, powder refuses new connections to the old container first (host `iptables` rule on the app's `127.0.0.1` port for nginx apps; a rule inside the container's network namespace for DNS-alias apps and for Traefik apps whose router carries a retry middleware), waits for its requests in flight, and only then stops it with SIGTERM and the service's `stop_grace_period` (30 s when unset). Before, `compose up --force-recreate` stopped it while the proxy still sent it requests: Traefik answered 502 for a refused port and a vanished container IP, and nginx lost POSTs that docker-proxy accepted for a stopped app or for a new container whose app was not listening yet. A rule cannot outlive its deploy: the exit trap deletes it before any output, a detached reaper (holding no lock) deletes it after the grace plus 240 s, the worker deletes the app's rules after a deploy that died without its trap, and the next deploy clears any left over. A `stop-drain` stability card names an app whose old container could not be routed away from (also a Traefik app with hand-written labels and no retry middleware), ignored SIGTERM or was killed with requests in flight. Rollout steps: "Stopping the old container without losing a request" in `/docs/deploys`.
- With the drain on for an app, the Traefik router powder renders for it carries a retry middleware (`<app>-retry`) that re-sends only requests that never reached a backend; with it off the labels are unchanged. Turning it on changes the router, which is not a lossy deploy: in drain mode the bridge carries its routers under their own names (`<router>-powder-bridge`), so it never conflicts with the old or the new container, and the hand-off only removes the bridge early when a service or middleware definition changes. New Traefik servers run with `--serverstransport.maxidleconnsperhost=-1`. The existing ones need it added by hand before the drain goes on there, which recreates Traefik (a short interruption for every app on that server, announce it): with flags in a compose file, add `--serverstransport.maxidleconnsperhost=-1` to the `traefik` service's command list; with a static `traefik.yml`, add `serversTransport:` with `maxIdleConnsPerHost: -1` at the top level; then `docker compose up -d traefik` in that directory.
- The servers list shows the URLs of apps behind a named nginx upstream. URL discovery only understood `proxy_pass http://<host>:<port>`, so on a server whose vhosts use the zero-downtime bridge layout (`upstream shop_app { server 127.0.0.1:3017 max_fails=0; server 127.0.0.1:13017 backup; }` with `proxy_pass http://shop_app;`) no container got a URL. A `proxy_pass` without a port that names an upstream of the same nginx (the host files, or one proxy container's `nginx -T`; never across the two) now resolves to that upstream's primary servers: `backup` and `down` entries, unix sockets and `[ipv6]` addresses are left out, so a hostname is never attached to the bridge port or to whatever else publishes it; an upstream may come after the server block that uses it; a name defined twice with different servers resolves to nothing (nginx refuses such a config, so neither copy is provably the running one). The direct and `set $var` forms parse as before. This also fills the hostnames in the generated deployment notes, the app context endpoint and the Domains page on those servers, and discovered hostnames there now become `pending` domain rows like on other servers (same rules: only from host nginx and proxy containers powder does not manage, never over an existing row). The TypeScript reader and the deploy-time awk upstream checks read a block the same way; a parity test feeds both the same nginx text.
- The servers list shows every URL of a container: the first two (one on phones, where the URLs now also appear under the name) and a `+N` toggle for the rest, which expands in place; wildcard hosts are text. Links are real links, opened in a new tab.
- A powder app with a live domain for which discovery finds no URL no longer shows a dash: the row shows the app's live domains from powder's domain record with the note "not found in the proxy config". The list API returns the number of such apps per server and in total (`liveAppsWithoutUrl`), near zero when discovery reads every proxy layout.
- Opening the servers page no longer writes false deploy history. The sync recorded a synthetic successful `image_update` deploy (`triggered_by=reconcile`) for any app whose image name started with `ghcr.io/` and whose last deploy had failed, so a locally built app tagged like a registry image flipped from failed to live after a real build or health-check failure. The reconcile now applies only to apps with `build_mode = 'registry'`, and only when the failed deploy recorded an image reference whose image id on the server differs from the running container's image id; the image name plays no part. A failed deploy records no image today, so in practice nothing is reconciled and a failure stays visible until a real deploy replaces it. Existing reconcile rows are not changed.
- URL discovery reads the host's full nginx config and `map $host` routing. On the host it reads the config only while a host proxy master runs: the pid file named by the config's `pid` directive, else the first existing of `/run/nginx.pid`, `/var/run/nginx.pid`, `/run/openresty.pid`, `/usr/local/openresty/nginx/logs/nginx.pid`, `/run/angie.pid` and `/var/run/angie.pid`, holds the pid of a live process named `nginx`, `openresty` or `angie` in the host's pid namespace (`/proc/<pid>/ns/pid` equal to pid 1's; an unreadable namespace counts as not running). A stopped nginx's leftover vhosts are not routing and no longer yield URLs or `pending` domain rows. For a running `nginx` master with the `nginx` binary on PATH it runs `nginx -T` (read-only, at most 6 s), so upstream and map blocks in `conf.d` or `nginx.conf` are seen; for an openresty or angie master, a running nginx whose binary is not on PATH, or a failing `nginx -T`, it reads `/etc/nginx/sites-enabled/*` and `/etc/nginx/conf.d/*.conf` (other config locations of openresty or angie are not read). Every file of that config is checked first: each `# configuration file` header of `nginx -T` (a name with a newline is checked by its first line), or each file of those two globs. If any resolves (`readlink -f`, so symlinks count by their target) under `/opt/apps` or its resolved path, nothing of the host config is read and the servers page says "host proxy config includes files from app space; routes not read"; if a header names a path that does not resolve to an existing file, nothing is read either and the page says "host proxy config names a file that could not be checked; routes not read". Both are logged as warnings. When the output is longer than 1,500,000 characters (the rest is not parsed) or the SSH output cap dropped part of it, this is logged and the page says "proxy config too large; some routes not read". A `proxy_pass` through a variable from `map $host` or `map $http_host` (`proxy_pass http://$app;`, `proxy_pass $app;` with a scheme in the value, or `proxy_pass http://127.0.0.1:$port;`) routes each `server_name` of that block that is an exact key of the map to that key's value only (an upstream name resolves as above); `default`, regex, wildcard and variable entries are skipped, and a map keyed on anything else is ignored. The servers list, the app context endpoint, the Domains page and the deployment notes see these hostnames.

### Added
- A copy control next to errors, logs and commands across the dashboard: the deployments tab, the deploy page, the ci tab, the deploys list, the activity feed, cron runs, backup and restore errors, domain errors, live logs, the unreachable-server card and the page that shows a new API token. It copies what the page shows. On a failed deploy it copies the app, deploy id, commit, failed step, exit code and the error text as one block.
- The domains tab says what the `www` host of a live apex domain does (and the apex of a `www` domain): redirects here, does not redirect here, redirects elsewhere, has no DNS record, or is broken with the HTTP status. powder asks the host itself, with one request it does not follow, and a recheck control asks again.
- The deploy history strip shows the day under the pointer at once, on hover, keyboard focus and tap: the weekday, the date in UTC and that day's deploy counts.

### Security
- powder's own images carry no package manager at runtime. The deploy's summary names the step and its failing lines. The proof must be in the failed step's own output (a lockfile error printed by an earlier `npm ci || npm install` that passed does not count), a TypeScript error needs a file position, and a step that ran out of memory or disk proves nothing. `POWDER_BUILDER_APP_VERDICT=off` in powder's env turns the rule off (every failed builder build falls back again). In the 30 days to 2026-11-19, 185 of the 195 pushes the 600 s window held had nothing to fold; a replay of those 30 days gives a median push-to-start wait of 0 s instead of 600 s, at 4295 deploys instead of 3361. `[urgent]`, **redeploy now**, rollbacks, stops and monorepo fan-out are unchanged.

It prunes nothing while a pull or build runs on the host (BuildKit can fail a running build whose parent snapshot is pruned): it waits up to 5 minutes, then only measures, and the run after the next build catches up. The builder's clone dir is removed after a successful build, and clones not built for a week are swept. A build host still over twice its cap, or with `/` at 85% or more, after the prune raises one deduped ops-endpoint warning (`POWDER_HQ_*`, `powder-build-host-disk`) that resolves itself.
- `powder-image-prune` keeps the newest rollback images per app and also removes dangling anonymous volumes (label `com.docker.volume.anonymous`) once they were created more than 7 days ago (`ANON_VOLUME_MAX_AGE_DAYS` in the cron line changes it), one by one with `docker volume rm`, and logs how many. A container removed without `-v` (`docker rm`, `docker compose down`, an app deleted in the dashboard) leaves its anonymous volumes behind. Named volumes are never removed: keep data in named volumes or bind mounts. Skipped like the image prune while a container start is in progress, and the build cache prune is skipped while a build or pull runs (the next hourly run catches up).
- First run: the first-run admin is stored in powder's database (`powder_meta`) and restored on start while `POWDER_ADMIN_USER_IDS` is empty, with a WARN to set it, so a restart before the env is set does not lock the owner out. The stored id is deleted at the first start with `POWDER_ADMIN_USER_IDS` set (and when a new first run begins), so removing an admin from the env later never brings them back. The log line, the setup checklist and the docs give the command that persists it and makes powder read the env file (`sudo bin/install.sh --set-admin <id>`); a plain restart does not.
- Memory cap per server is an operator opt-in: with `/opt/apps/.mem-cap` on a server, every deploy sets that cap on the app container, overriding a compose `mem_limit`, and sets `restart: unless-stopped` only where the restart policy is none (docs: "The standard app shape on a server"). Without the file a deploy leaves both alone. The optional `powder-resource-guard`, if installed, caps every container without a memory limit at 2g when the file is absent.
- Previews on an origin-cert server serve the origin certificate (`tls=true`) like the app. One helper writes the TLS setting of every Traefik router powder creates.
- Previews build the app's own Dockerfile and route to its container port (stored at `/new`, editable under Settings, preview deploys); with no port set, it is read from the app's compose labels.
- Preview deploys never run the `powder.release.cmd` release command (`[release] skipped: preview deploys never run the release command`), as they never run `powder-migrate`: a preview cannot apply the branch's unmerged migrations to the app's database.
- Migrations with your own runner: an app whose migrations are code runs its own ledgered migrator from `LABEL powder.release.cmd` (for example `knex migrate:latest`, `prisma migrate deploy`), once per deploy before the swap. A schema push there raises the `release-cmd` deploy-setup warning. See /docs/deploys#migrations-with-your-own-runner.
- `powder-migrate` applies each transactional migration file with `lock_timeout` 10s (sent with the connection as `PGOPTIONS`, so it replaces a role or database `lock_timeout`): a file blocked behind another session's lock fails with `canceling statement due to lock timeout` and the deploy stops before the swap while the old container keeps serving. A file that needs longer sets `SET lock_timeout` itself. Files run outside a transaction (`CONCURRENTLY`, `ALTER TYPE ... ADD VALUE`) get no timeout. `POWDER_MIGRATE_LOCK_TIMEOUT` (`0` or 1s to 600s) changes the default when it is in the helper's environment; powder does not pass it. A `DATABASE_URL` through a pooler that refuses startup options (PgBouncer without `options` in `ignore_startup_parameters`) fails to connect.
- `powder-migrate` never records a non-transactional file while an index its SQL names (comments left out; whole word, any case, quoted or schema-qualified) is INVALID, whether it was invalid before the file ran or not, or while an index that turned invalid during the file is INVALID (unless another session's concurrent build of it is still running), so a retry that `IF NOT EXISTS` skips fails again instead of being recorded over a broken index. The log names the indexes and the fix (`DROP INDEX CONCURRENTLY`, fix the cause, redeploy), also when the file itself fails. An unrelated invalid index the file does not name never fails it, and a catalog query that fails only logs a warning.
- The worker waits at start until the `powder` container has applied the pre-deploy migrations of its image (up to `POWDER_WORKER_MIGRATION_WAIT` seconds, default 600), so it never runs new code on the old schema.
- API: `GET` container inspect, env-file and git-status answer 404 (`no_container`), 503 (`server_unreachable`) or 502 (`remote_failed`) with a `code` field. The domains `GET` returns the server's `ingressIp`, the server `GET` returns the pinned SSH `hostKeyFingerprint`, and the users API returns `isAdmin` for each user.
- Deploy-setup warnings behind `POWDER_STABILITY_CARDS` (default off: each card is only logged as `[stability] would warn: <key> <reason>`; `on` posts it as an ops endpoint warning card). Warnings only: no deploy fails, waits or changes because of them, and a check that cannot finish raises and clears nothing. See /docs/deploys#deploy-setup-warnings.
  - Bridge verdicts `nginx-unbridged` and `host-network` for an app traefik does not route and that has no bridge label: `nginx-unbridged` when host nginx (`nginx -T`, read-only) proxies to the container's published `127.0.0.1` port, `host-network` for `network_mode: host`. Any failure to read docker or nginx gives `not-routed`. With the switch on they raise `no-bridge:<server>/<app>` with what to change.
  - `compose-drift:<server>/<app>`: the repo's `docker-compose.yml` differs from the runtime compose (the `[compose-drift] WARNING` of the deploy log); the card clears on the next deploy without drift.
  - `migrate-path:<server>/<app>`: a read-only scan right before `db migrate` (bounded `find`, `docker image inspect` capped by `timeout`) reports schema changes that bypass `powder-migrate`: migration-looking `*.sql` files outside the folders it reads while none of those holds one (`stray-sql`), or a schema tool in the image command (`boot-cmd`), the `powder.release.cmd` label (`release-cmd`) or `package.json` `start` (`start-script`). An app in the workdir layout gets no `*.sql` walk (its app dir also holds data and backups).
  - `health-url:<server>/<app>`: the app has no health URL, so the health gate passes on any 1xx-4xx answer from `/`. Raised only when the gate judged HTTP (not for a worker on the liveness fallback, not for previews); setting a health URL on the app's Settings tab clears it on the next deploy.
  - `test-gate:<server>/<app>`: the build context has no `.powder/test.sh` (a prebuilt deploy checks the synced context on the target).
  - The checks report through nonce-tagged marker lines (`__POWDER_STAB_<nonce>__ <kind> <value>`), so build or test output cannot forge them, and the card text is fixed per condition: nothing from the deploy log is sent.

### Security
- `BETTER_AUTH_URL` is required in production: powder and the worker refuse to start without a valid http(s) value. Webhook URLs, alert and deploy-log links, generated `AGENTS.md` / `DEPLOYMENT.md`, the env-file header and the MCP origin are built from it. Creating or connecting an app refuses with a clear error instead of installing a webhook without it.
- Webhooks: capped request bodies, signed repository id check, already-deployed commits skipped, DNS-rebinding check on notification webhook targets.
- Deploys: one compose authority (powder's own override file, the app's compose is never edited), symlink guards, CR/LF refused in labels, hostnames revalidated before they reach a Traefik rule, secrets and scripts delivered over SFTP at 0600 instead of argv.
- Auth: one-time setup token on first run, per-email sign-in lockout, configurable trusted client-IP header. better-auth endpoints the dashboard does not use (session listing and revoking, user and email updates, account linking, password reset, email verification, user delete) answer 404.
- Backups: unique S3 key per backup, sha256 check on restore, presigned URLs kept off argv, 0600 logs and status files.
- Backups: scheduled and manual backups are separate retention pools. A scheduled success keeps the newest `BACKUP_KEEP_PER_APP` scheduled ones, a manual success the newest `BACKUP_KEEP_MANUAL_PER_APP` manual ones (default 3), so a manual backup (an API token may trigger one) never deletes a scheduled one. One backup runs per app at a time (a second trigger gets 409; a run still marked running past the 24 h upload window is closed and replaced), an API token can trigger 2 backups per app per 10 minutes, and every caller except an admin browser session at most 12 manual backups per app per 24 hours, counted from the database (then 429). The watchdog aborts the multipart upload of a failed backup that still holds one. Migration `0064_app_backups_in_flight.sql` adds the `source` column and the one-in-flight index.
- Deploy webhook: the per-token rate limit counts only requests with a valid signature, so unsigned or badly signed requests cost only the per-IP limit and cannot block real deliveries. `GET /api/projects/<id>` returns the webhook URL with a `<token>` placeholder to API token callers. A well-formed token that names no app answers 401 `bad signature`, like a valid token with a wrong signature, after the same database lookups and HMAC work.
- Web: security headers and CSP on all routes, no `X-Powered-By`, bounded regexes for log parsing and masking.
- Disconnecting an app removes the deploy key and webhook powder installed on GitHub.
- A GitHub hook that keeps posting to a deploy token powder no longer has is removed from the repository by powder, only when the repository is one powder manages, the token is unknown at both checks (before the GitHub calls and right before the delete), and the hook's own URL is this powder's `/api/webhooks/deploy/<that token>`; one attempt per hook id and at most 30 in all per 10 minutes, counted only for managed repositories. Docs: "Webhooks" in `/docs/security-model`.
- Uptime checks and notification webhooks refuse the cloud metadata address 100.100.100.200 (inside 100.64/10, which they otherwise allow for private overlay networks).
- Startup refuses weak `BETTER_AUTH_SECRET` / `POWDER_ENCRYPTION_KEY` values and warns on a non-https `BETTER_AUTH_URL`.
- powder's base image (`node:22-bookworm-slim`) and the bootstrap Traefik are pinned by digest; the Docker install step prints and can verify the install script's sha256 (`POWDER_GET_DOCKER_SHA256`).
- Compose guard, builds, env files, git, registry logins, crons, backups and the API: the compose and build rules are described in [docs/SECURITY-COMPOSE.md](https://github.com/powder-sh/powder/blob/main/docs/SECURITY-COMPOSE.md).
- Builds: the Dockerfile check reads line continuations exactly as BuildKit does (a line ending in an escaped escape character does not continue, a continued line keeps its leading whitespace, comment and blank lines inside a continuation are skipped), so a crafted Dockerfile cannot hide an instruction, flag or `ADD` source from the build rules. A line ending in two or more escape characters, and a `RUN` / `COPY` / `ADD` / `FROM` flag glued to a line continuation, are refused, and so is any heredoc `<<` form other than a whole-word `<<NAME` / `<<-NAME` / `<<"NAME"` / `<<'NAME'` (`<< EOF`, `<<<`, `cat<<EOF`) and a Unicode space outside quotes in an instruction. An image ref that uses one of BuildKit's automatic args (`TARGETSTAGE`, the platform ones) is refused, a `FROM` with a variable naming a stage is written back as that stage, and a `COPY --from=` number too long for a stage index is checked as an image.
