# Changelog

All notable changes to powder are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow
[Semantic Versioning](https://semver.org/).

## [0.10.0] - 2026-11-17

First public release.

### Highlights
- One-command install: `sudo bin/install.sh` in a checkout on the server sets up the SSH key, a 0600 env file with new secrets, Traefik, powder, its database and the worker, and waits for `/api/health`. `sudo bin/install.sh --set-admin <id>` persists the first admin.
- The schema is created automatically on an empty database, and the `powder` container applies pending migrations on every start. No SQL by hand.
- Stop, start and delete an app from its settings page (danger zone), and delete a server once no app is left on it.
- One status vocabulary for apps and deploys across the dashboard, with a `?status=` filter on the apps list, and an unreachable server told apart from a missing or stopped container, with a way forward.
- Safe defaults for a public install: the compose guard enforces, powder and its worker run without capabilities, powder's database sits on a private network and builds pull their base images. Each has an opt-out in the env file (see "The env file" in `/docs/self-hosting`).
- Managed crons, notification targets (webhooks and email), backup restore into a new database and an activity feed, all in the dashboard.

### Added
- Single-tenant: one install serves one operator; other accounts are refused.
- Swap-check: a deploy only swaps the container after the new one passes its health check, and the old container keeps serving otherwise.
- Traefik per server as the reverse proxy, with a per-server base domain for default app hosts and previews.
- Schema-before-code self-deploys: `bin/self-deploy.sh` applies database migrations before it builds and recreates anything.
- Public documentation under `/docs`.
- Daily update check against the public GitHub releases (disable with `POWDER_UPDATE_CHECK=off`), a notice in the dashboard, and the running version on the sidebar and in `/api/health`.
- Zero-downtime bridge, opt-in with the label `powder.bridge.enabled=true` on the running container: before `db migrate` powder starts a copy of the running container from its current image, waits until it answers, recreates the app, waits until the new container answers, then drains and removes the copy. A deploy never fails because of the bridge: when it cannot run, the log says `[bridge] skipped: <reason>`. Traefik apps need a Docker healthcheck and explicit Traefik router and service labels. A traefik-routed app whose every host port binding is on `127.0.0.1` / `::1` (e.g. `127.0.0.1:3040:3000`) is bridged too, and the copy publishes no ports; a binding on any other interface skips as its own verdict `host-ports`, whose ops endpoint warning card names the compose ports line to drop. The bridge reads the container's labels with `docker inspect -f` and drops the one empty line docker prints after the template; an LF or CR inside a label is refused. A trip of that self-check reports verdict `internal`, whose ops endpoint warning card says it is a powder bug, not an app setting, and asks for a report on the public issue tracker.
- Zero-downtime bridge for nginx-fronted apps: with the label `powder.bridge.host-port=<N>` next to `powder.bridge.enabled=true`, an app that publishes one tcp port on `127.0.0.1` gets a bridge published on `127.0.0.1:<N>` during the swap (N must be that port + 10000) (no traefik labels or docker healthcheck needed). Add it to the vhost as `server 127.0.0.1:<N> backup;` with `proxy_next_upstream error timeout;` and the 502s during the container swap go away. Docs: "Zero-downtime bridge" in `/docs/deploys`. In this mode the bridge copies `extra_hosts` (validated `name:ip` / `name:host-gateway`) instead of skipping; traefik mode still skips on them.
- Host nginx check on every deploy: on a server with an `nginx` binary, each deploy runs a read-only `nginx -T` (20 s limit when `timeout` is installed) and logs every upstream whose only primary server lacks `max_fails=0` next to a `backup` server (one slow response marks that primary down, and nginx answers 502/503 until the backup is up), and, for an app in bridge host-port mode, whether an upstream lists `server 127.0.0.1:<N> backup;`. With the ops endpoint set (`POWDER_HQ_*`) each finding is a deduped warning card, one per server and one per app, that clears on the next deploy that finds none. It never fails a deploy. Docs: "Zero-downtime bridge" in `/docs/deploys`.
- Settle window for push deploys, off by default: a push deploy waits up to the set number of seconds (at most 1800, counted from the first push) so further pushes fold into it and ship as one deploy of the newest commit. Set per app on the Settings tab ("settle window", or `deploySettleSeconds` in `PATCH /api/projects/<id>`; empty or `null` = the install default, `0` = never wait; the install default is `POWDER_DEPLOY_SETTLE_SECONDS` in the env file, applied when powder starts). A waiting deploy stays `queued` and says `waiting until HH:MM UTC to bundle further pushes`. Lowering the window does not shorten a wait already running; `0`, "redeploy now" or an `[urgent]` push releases it. A push with `[urgent]` in any commit message (any case), a signed `powder_force`, and "redeploy now" in the dashboard deploy at once and release a waiting deploy; manual redeploys, rollbacks, restarts, starts, stops and previews never wait. A rollback or stop cancels a waiting push (step `superseded`). Docs: "Bundling quick pushes" in `/docs/deploys`.
- Deploy failures that ran out of memory say which kind and how to fix it, with a stable prefix for cards and robots: `heap-oom:` when the output has a V8 heap signature (`JavaScript heap out of memory`, `Reached heap limit`, `Ineffective mark-compacts`, `Allocation failed - JavaScript heap`): set `NODE_OPTIONS=--max-old-space-size=<MB>` on that step (`.powder/test.sh` line or Dockerfile `ENV`), it is not a code bug; `container-oom:` when the process was SIGKILLed (test gate exit 137, a docker build RUN `exit code: 137`, `OOMKilled: true`): add memory or swap on the server (for the test gate, also raise `POWDER_TESTGATE_MEM` when it is set), the heap flag does not help. The test gate's FAILED line carries its exit code.
- `GET /api/internal/auto-rollback?deploy=<id>` (admin, read-only): the preflight a monitor or ops tool calls before rolling an app back on its own. It names the deploy to roll back to (the image that ran before) and blocks powder's own containers, `POWDER_AUTO_ROLLBACK_NEVER`, apps with automatic rollback turned off (a toggle on the app's Settings tab, or `autoRollback` in `PATCH /api/projects/<id>`; on by default), a deploy that is not the latest or is over 25 minutes old, a missing previous image, an unreadable diff, and a diff that changes the database schema unless every change is an added .sql migration of additive statements or carries `-- powder:reversible`, and destructive DDL added outside .sql files (code that changes the schema at boot). The rollback itself is the existing rollback route. Docs: "Rollback preflight for monitors" in `/docs/deploys`.
- Remote MCP server at `POST /api/mcp` (bearer API tokens only) so coding agents can list apps, read deploy logs, redeploy and manage env vars, each tool limited to its token scope. Coding agent token presets and connect snippets on the API tokens page. Docs: `/docs/mcp`.
- "Ask your agent" prompts in the dashboard and on the homepage, and `/llms.txt`.
- Activity feed: one read-only timeline of non-git deploys, failed deploys, env changes, backups and restores, with filters and paging.
- Optional host split: `POWDER_SITE_HOST` serves only the public site, docs, webhooks and health on its own host, with the dashboard on a separate dashboard host (`BETTER_AUTH_URL`).
- Server settings in the dashboard: `proxy`, `tls_mode`, `base_domain`, `ingress_ip` and the dedicated builder (`build_host`) are edited on each server's page (or `PATCH /api/servers/<id>`), with a DNS check for the wildcard record. No SQL needed.
- App settings tab: health URL, uptime checks and preview deploys are switched on per app there (or `PATCH /api/projects/<id>` with `healthUrl`, `uptimeEnabled`, `previewsEnabled`). No SQL needed.
- Server bootstrap, check first: "Check server" reports, over SSH, Docker and the compose plugin, the `web` and `internal` networks, Traefik and its file provider (Traefik servers), `/opt/apps` and the Traefik dynamic dir, ufw, disk and memory, `git` and `flock` (required, installed with the distro's package manager), the helpers `powder-migrate` and `powder-image-prune`, the prune's cron file, Traefik log rotation (Traefik servers), and whether the optional `powder-resource-guard` is there. "Fix missing pieces" only adds what is missing (Docker, networks, directories, the two helpers, the cron file, Traefik log rotation in `/etc/logrotate.d/powder-traefik` on Traefik servers, Traefik) and never touches an existing proxy, firewall, container, cron or logrotate file; replacing an outdated helper is a separate, unticked choice. Also as `bin/server-bootstrap.sh` (`--replace-helpers` for the replacement).
- First-run checklist on the dashboard: OAuth, servers, SSH, server check, base domain and DNS, backups, notifications, admin id.
- Notification targets: several webhooks and email (SMTP via `POWDER_SMTP_URL` and `POWDER_MAIL_FROM`), each subscribed to events (deploy failed or succeeded, app down or up, backup failed or stale, cron failed) and optionally one app. `POWDER_NOTIFY_WEBHOOK_URL` adds one always-on webhook from the env file.
- Managed crons: per-app HTTP and `docker exec` jobs that powder schedules, runs, logs and alerts on, with timezones, overlap protection and "run now". Host crontab lines can be imported.
- Backup restore: download a backup with the exact decrypt commands, restore into a new database next to the live one, verify a backup, and drop restore databases. The live database is never touched.
- Backups tab: a database form sets which Postgres an app backs up (container, or host for Postgres outside Docker, database, user and a password stored encrypted), and turns backups on for an app without a database of its own. Admin browser session only; `PATCH /api/projects/<id>` takes the same fields (`hasPostgres`, `backupDbContainer`, `backupDbHost`, `backupDbName`, `backupDbUser`, `backupDbPassword`).
- The `powder` container applies pending migrations on start, so `docker compose up -d` with a new image upgrades the schema too (`POWDER_MIGRATE_ON_BOOT=off` to opt out).
- Swap-check probes `/api/auth/get-session` on better-auth apps and fails the swap on a 5xx (schema mismatch). Opt out with `POWDER_AUTH_CHECK=off` per app or `POWDER_SWAP_CHECK_AUTH=off` for every app.
- Hardening for powder itself, on by default: no capabilities and `no-new-privileges` for powder and the worker, powder's DB on its own private network, `--pull` on builds, and the compose guard in enforce mode. `POWDER_WEB_READONLY=true` adds a read-only web root filesystem. Each has an opt-out in the env file.
- `bin/install.sh`: install or re-run powder on its own server from a checkout there. Checks docker, docker compose 2.24 or newer, openssl, git, curl, ssh-keygen and awk; creates the SSH key powder uses and `/opt/apps/powder.env` from `docker/powder.env.example` (mode 0600, new secrets and database password); creates the `web` network; runs `bin/server-bootstrap.sh` on the server (the networks, the helpers and the prune's cron, Traefik when the server has no proxy; `--no-proxy` skips it); builds and starts powder and postgres, then the worker once powder serves, and waits for `/api/health` to report ok; prints the next steps. Before the build it checks that the dashboard host resolves to this server and warns with the fix when it does not (Let's Encrypt cannot issue the certificate then), and warns when memory plus swap is under 2 GB, since powder's own image is built there; neither blocks. `--dry-run` prints the plan, `--yes` installs a missing Docker without asking, `--set-admin <id>` persists the first admin. Re-running never replaces an existing env file. A re-run (the on-server upgrade) refuses while deploys are in flight and waits up to 45 minutes for ones that start during the build (`--force` skips that); keeps `--no-proxy` (stored as `POWDER_PROXY=none`; `--proxy` overrides it for one run); accepts a `BETTER_AUTH_URL` with `http` or a port; writes a non-default `POWDER_ENV_FILE` into the env file and refuses a path an app could own (`/opt/apps/<name>.env`, `/opt/apps/<name>/`); refuses a symlinked env file; removes its secret temp files when interrupted; and lets docker compose read its values from the env file only (a shell variable such as `SSH_KEY_PATH` is ignored, with a notice).
- Fresh database: `bin/lib-migrations.sh` detects an empty database (empty ledger and none of the tables the migration files create) and, with `POWDER_ALLOW_FRESH_SCHEMA=1`, applies every file in filename order, recording each in the transaction that applies it. Without that setting an empty database is refused (a wrong `DATABASE_URL` looks the same); `bin/install.sh` sets it on a new server and removes it once the schema exists, and `pnpm db:init` sets it. A marker row lets a half-finished first start resume. A file runs outside a transaction only when its SQL, comments left out, uses `CONCURRENTLY` or `ALTER TYPE ... ADD VALUE`, the same rule as `powder-migrate` on the app servers.
- App settings: a danger zone with stop, start and delete. Stop runs `docker stop` on the app container with the same access as restart and records a deploys row of kind `stop` (per-app in-flight lock, activity feed). Start runs the compose guard, then `compose up` of the app service. Delete needs an admin browser session and the typed app name: under the per-app deploy lock it removes the app container and, when the compose project is the app's own, every container and network of that project (never volumes, directories or files; an anonymous volume left dangling is removed by `powder-image-prune` once it is older than its grace, 7 days by default), tears down previews, does what a repo disconnect does (deploy key, GitHub deploy key and webhook, app row, env file archive) and removes the app's crons and domains. A failed removal keeps every row. Recorded as a deploys row of kind `delete`; migration `0059_deploy_kind_stop_delete.sql` adds both kinds.
- App logs tab: a runtime view (live container logs, the default) next to the deploy output, and a note when the app has no container yet.
- `POWDER_RESERVED_APP_NAMES`: a comma-separated list of extra names `/new` and the adopt flows refuse (app-name shape, lowercased, at most 64).
- Docs pages: Quickstart (first in the index), What your repo needs, Troubleshooting, Upgrading and Uninstall; `llms.txt` lists them.
- A not-found page, and an error boundary and loading state for the dashboard. The error page offers a retry and a link back to the apps list and shows only the error digest.
- Remove a user at `/admin/users` (`DELETE /api/admin/users/<id>`, admin browser session only): deletes their sessions, sign-in methods, API tokens and stored integration tokens. Admin ids and your own id are refused.
- Delete a server from its page once no app is left on it. The API refuses with 409 `server_has_apps` while one is, and only powder's record is removed: the machine keeps running.
- Domains tab: the A or CNAME and TXT records to create for each domain, the last verification error and "check again".
- `/new` shows a server picker when there is more than one compose server, and says why when no server can take the app.
- Apps list: a `?status=` filter (`live`, `deploying`, `failed`, `down`, `unknown`), kept in the URL.
- Docs: a copy button on every command block, a contents rail and previous and next links.
- `GET /api/sign-in-link` (no session needed): whether the public pages show a sign-in link.
- `pnpm db:init` creates or updates a development database with the same rules as the production boot step (`bin/db-init.sh`, needs `psql`), `pnpm lint` runs `biome lint` over the repo, and `CONTRIBUTING.md` covers the dev loop, the checks and the migration rules.
- Design: tokens with AA contrast in both themes, shared UI primitives, phone layouts, empty and error states, an apps table with filters and per-app deploy strips, and the "live wire" look for the public site, docs, login and Open Graph cards.
- Secrets are masked when deploy, cron and backup output is written, not only when shown, by one shared masking authority. Env value previews store the length only.
- DEPLOYMENT.md sync into app repos is opt-in per app (off by default). `/new` commits an `AGENTS.md` only when you tick it and the repo has none; it describes what a push does, where env vars live and how to check a deploy.
- Traefik is the documented proxy and the default for new servers; the nginx and nginx-container modes work without custom domains, previews, snapshots or traffic stats, and `/domains` lists only nginx servers.
- Deploy failure summaries for a missing or denied image point at the Dockerfile `FROM` lines.
- Compose guard: when it refuses because the compose config differs from the last successful deploy, it lists what changed, per service and key (`services.app.network_mode: host -> (unset)`, `services.app.ports: added 127.0.0.1:3000:3000`, `services.app.labels: added powder.bridge.enabled`), and says that a hand edit of the server compose causes this as much as a repo commit. A success stores a view of the compose structure for the diff (`deploys.compose_config_view`, migration 0062): labels, build, command and other secret-bearing keys keep only key names and hashes keyed by `POWDER_ENCRYPTION_KEY` and a per-view salt, and no environment value is ever stored or printed.
- Compose guard rule `env_loopback` (high severity), run when the compose structure changed: a service that is not on host networking whose env (env_file contents or `environment:`) tells it to connect to `127.0.0.1`, `localhost` or `[::1]` on a port it does not listen on itself is refused, since inside a bridge container loopback is the container itself. Only connection targets count (backend-scheme URLs anywhere; http(s) URLs in `*_URL` / `*_HOST` / `*_ENDPOINT` style names; bare host:port in `*_HOST` / `*_ADDR` names), never CORS / allowed-host / public / redirect / site / auth URL variables. Its own ports (`PORT`, container ports, `expose`, the running image's EXPOSE ports, a Traefik service port label, its healthcheck port) pass, and services sharing a namespace via `network_mode: service:<x>` are skipped. Exemptable by variable name: `POWDER_COMPOSE_GUARD_EXEMPT={"<server>/<app>":{"env_loopback":["DATABASE_URL"]}}`. See docs/SECURITY-COMPOSE.md.
- Dedicated build hosts (`servers.build_host`) keep their disk bounded: after every builder phase powder runs a cap prune on the build host (in the background, one at a time) that checks the `docker buildx du` Total, shared records included, and prunes build cache by age in steps (24h down to 1h) until it is under `POWDER_BUILDER_CACHE_CAP_GB` (default 30). It prunes nothing while a pull or build runs on the host (BuildKit can fail a running build whose parent snapshot is pruned): it waits up to 5 minutes, then only measures, and the run after the next build catches up. The builder's clone dir is removed after a successful build, and clones not built for a week are swept. A build host still over twice its cap, or with `/` at 85% or more, after the prune raises one deduped ops-endpoint warning (`POWDER_HQ_*`, `powder-build-host-disk`) that resolves itself.
- `powder-image-prune` keeps the newest rollback images per app and also removes dangling anonymous volumes (label `com.docker.volume.anonymous`) once they were created more than 7 days ago (`ANON_VOLUME_MAX_AGE_DAYS` in the cron line changes it), one by one with `docker volume rm`, and logs how many. A container removed without `-v` (`docker rm`, `docker compose down`, an app deleted in the dashboard) leaves its anonymous volumes behind. Named volumes are never removed: keep data in named volumes or bind mounts. Skipped like the image prune while a container start is in progress, and the build cache prune is skipped while a build or pull runs (the next hourly run catches up).
- First run: the first-run admin is stored in powder's database (`powder_meta`) and restored on start while `POWDER_ADMIN_USER_IDS` is empty, with a WARN to set it, so a restart before the env is set does not lock the owner out. The stored id is deleted at the first start with `POWDER_ADMIN_USER_IDS` set (and when a new first run begins), so removing an admin from the env later never brings them back. The log line, the setup checklist and the docs give the command that persists it and makes powder read the env file (`sudo bin/install.sh --set-admin <id>`); a plain restart does not.
- Memory cap per server is an operator opt-in: with `/opt/apps/.mem-cap` on a server, every deploy sets that cap on the app container, overriding a compose `mem_limit`, and sets `restart: unless-stopped` only where the restart policy is none (docs: "The standard app shape on a server"). Without the file a deploy leaves both alone. The optional `powder-resource-guard`, if installed, caps every container without a memory limit at 2g when the file is absent.
- Previews on an origin-cert server serve the origin certificate (`tls=true`) like the app. One helper writes the TLS setting of every Traefik router powder creates.
- Previews build the app's own Dockerfile and route to its container port (stored at `/new`, editable under Settings, preview deploys); with no port set, it is read from the app's compose labels.
- Preview deploys never run the `powder.release.cmd` release command (`[release] skipped: preview deploys never run the release command`), as they never run `powder-migrate`: a preview cannot apply the branch's unmerged migrations to the app's database.
- Migrations with your own runner: an app whose migrations are code runs its own ledgered migrator from `LABEL powder.release.cmd` (for example `knex migrate:latest`, `prisma migrate deploy`), once per deploy before the swap. A schema push there raises the `release-cmd` deploy-setup warning. See /docs/deploys#migrations-with-your-own-runner.
- `powder-migrate` applies each transactional migration file with `lock_timeout` 10s (sent with the connection as `PGOPTIONS`, so it replaces a role or database `lock_timeout`): a file blocked behind another session's lock fails with `canceling statement due to lock timeout` and the deploy stops before the swap while the old container keeps serving. A file that needs longer sets `SET lock_timeout` itself. Files run outside a transaction (`CONCURRENTLY`, `ALTER TYPE ... ADD VALUE`) get no timeout. `POWDER_MIGRATE_LOCK_TIMEOUT` (`0` or 1s to 600s) changes the default when it is in the helper's environment; powder does not pass it. A `DATABASE_URL` through a pooler that refuses startup options (PgBouncer without `options` in `ignore_startup_parameters`) fails to connect.
- `powder-migrate` never records a non-transactional file while an index its SQL names (comments left out; whole word, any case, quoted or schema-qualified) is INVALID, whether it was invalid before the file ran or not, or while an index that turned invalid during the file is INVALID (unless another session's concurrent build of it is still running), so a retry that `IF NOT EXISTS` skips fails again instead of being recorded over a broken index. The log names the indexes and the fix (`DROP INDEX CONCURRENTLY`, fix the cause, redeploy), also when the file itself fails. An unrelated invalid index the file does not name never fails it, and a catalog query that fails only logs a warning.
- The worker waits at start until the `powder` container has applied the pre-deploy migrations of its image (up to `POWDER_WORKER_MIGRATION_WAIT` seconds, default 600), so it never runs new code on the old schema.
- API: `GET` container inspect, env-file and git-status answer 404 (`no_container`), 503 (`server_unreachable`) or 502 (`remote_failed`) with a `code` field. The domains `GET` returns the server's `ingressIp`, the server `GET` returns the pinned SSH `hostKeyFingerprint`, and the users API returns `isAdmin` for each user.
- Deploy-setup warnings behind `POWDER_STABILITY_CARDS` (default off: each card is only logged as `[stability] would warn: <key> <reason>`; `on` posts it as an ops endpoint warning card). Warnings only: no deploy fails, waits or changes because of them, and a check that cannot finish raises and clears nothing. See /docs/deploys#deploy-setup-warnings.
  - Bridge verdicts `nginx-unbridged` and `host-network` for an app traefik does not route and that has no bridge label: `nginx-unbridged` when host nginx (`nginx -T`, read-only) proxies to the container's published `127.0.0.1` port, `host-network` for `network_mode: host`. Any failure to read docker or nginx gives `not-routed`. With the switch on they raise `no-bridge:<server>/<app>` with what to change.
  - `compose-drift:<server>/<app>`: the repo's `docker-compose.yml` differs from the runtime compose (the `[compose-drift] WARNING` of the deploy log); the card clears on the next deploy without drift.
  - `migrate-path:<server>/<app>`: a read-only scan right before `db migrate` (bounded `find`, `docker image inspect` capped by `timeout`) reports schema changes that bypass `powder-migrate`: migration-looking `*.sql` files outside the folders it reads while none of those holds one (`stray-sql`), or a schema tool in the image command (`boot-cmd`), the `powder.release.cmd` label (`release-cmd`) or `package.json` `start` (`start-script`). An app in the workdir layout gets no `*.sql` walk (its app dir also holds data and backups).
  - `health-url:<server>/<app>`: the app has no health URL, so the health gate passes on any 1xx-4xx answer from `/`. Raised only when the gate judged HTTP (not for a worker on the liveness fallback, not for previews); setting a health URL on the app's Settings tab clears it on the next deploy.
  - `test-gate:<server>/<app>`: the build context has no `.powder/test.sh` (a prebuilt deploy checks the synced context on the target).
  - The checks report through nonce-tagged marker lines (`__POWDER_STAB_<nonce>__ <kind> <value>`), so build or test output cannot forge them, and the card text is fixed per condition: nothing from the deploy log is sent.

### Security
- `BETTER_AUTH_URL` is required in production: powder and the worker refuse to start without a valid http(s) value. Webhook URLs, alert and deploy-log links, generated `AGENTS.md` / `DEPLOYMENT.md`, the env-file header and the MCP origin are built from it. Creating or connecting an app refuses with a clear error instead of installing a webhook without it.
- Webhooks: capped request bodies, signed repository id check, already-deployed commits skipped, DNS-rebinding check on notification webhook targets.
- Deploys: one compose authority (powder's own override file, the app's compose is never edited), symlink guards, CR/LF refused in labels, hostnames revalidated before they reach a Traefik rule, secrets and scripts delivered over SFTP at 0600 instead of argv.
- Auth: one-time setup token on first run, per-email sign-in lockout, configurable trusted client-IP header. better-auth endpoints the dashboard does not use (session listing and revoking, user and email updates, account linking, password reset, email verification, user delete) answer 404.
- Backups: unique S3 key per backup, sha256 check on restore, presigned URLs kept off argv, 0600 logs and status files.
- Backups: scheduled and manual backups are separate retention pools. A scheduled success keeps the newest `BACKUP_KEEP_PER_APP` scheduled ones, a manual success the newest `BACKUP_KEEP_MANUAL_PER_APP` manual ones (default 3), so a manual backup (an API token may trigger one) never deletes a scheduled one. One backup runs per app at a time (a second trigger gets 409; a run still marked running past the 24 h upload window is closed and replaced), an API token can trigger 2 backups per app per 10 minutes, and every caller except an admin browser session at most 12 manual backups per app per 24 hours, counted from the database (then 429). The watchdog aborts the multipart upload of a failed backup that still holds one. Migration `0064_app_backups_in_flight.sql` adds the `source` column and the one-in-flight index.
- Deploy webhook: the per-token rate limit counts only requests with a valid signature, so unsigned or badly signed requests cost only the per-IP limit and cannot block real deliveries. `GET /api/projects/<id>` returns the webhook URL with a `<token>` placeholder to API token callers. A well-formed token that names no app answers 401 `bad signature`, like a valid token with a wrong signature, after the same database lookups and HMAC work.
- Web: security headers and CSP on all routes, no `X-Powered-By`, bounded regexes for log parsing and masking.
- Disconnecting an app removes the deploy key and webhook powder installed on GitHub.
- A GitHub hook that keeps posting to a deploy token powder no longer has is removed from the repository by powder, only when the repository is one powder manages, the token is unknown at both checks (before the GitHub calls and right before the delete), and the hook's own URL is this powder's `/api/webhooks/deploy/<that token>`; one attempt per hook id and at most 30 in all per 10 minutes, counted only for managed repositories. Docs: "Webhooks" in `/docs/security-model`.
- Uptime checks and notification webhooks refuse the cloud metadata address 100.100.100.200 (inside 100.64/10, which they otherwise allow for private overlay networks).
- Startup refuses weak `BETTER_AUTH_SECRET` / `POWDER_ENCRYPTION_KEY` values and warns on a non-https `BETTER_AUTH_URL`.
- powder's base image (`node:22-bookworm-slim`) and the bootstrap Traefik are pinned by digest; the Docker install step prints and can verify the install script's sha256 (`POWDER_GET_DOCKER_SHA256`).
- Compose guard, builds, env files, git, registry logins, crons, backups and the API: the compose and build rules are described in [docs/SECURITY-COMPOSE.md](https://github.com/powder-sh/powder/blob/main/docs/SECURITY-COMPOSE.md).
- Builds: the Dockerfile check reads line continuations exactly as BuildKit does (a line ending in an escaped escape character does not continue, a continued line keeps its leading whitespace, comment and blank lines inside a continuation are skipped), so a crafted Dockerfile cannot hide an instruction, flag or `ADD` source from the build rules. A line ending in two or more escape characters, and a `RUN` / `COPY` / `ADD` / `FROM` flag glued to a line continuation, are refused, and so is any heredoc `<<` form other than a whole-word `<<NAME` / `<<-NAME` / `<<"NAME"` / `<<'NAME'` (`<< EOF`, `<<<`, `cat<<EOF`) and a Unicode space outside quotes in an instruction. An image ref that uses one of BuildKit's automatic args (`TARGETSTAGE`, the platform ones) is refused, a `FROM` with a variable naming a stage is written back as that stage, and a `COPY --from=` number too long for a stage index is checked as an image.
